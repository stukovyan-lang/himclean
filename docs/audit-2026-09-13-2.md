Повторный замер после фазы 4b: два дефекта контраста устранены системно, LCP

## LCP: что за элемент и что с ним сделано

LCP-элементом на всех четырёх маршрутах оказался не заголовок, а вводный
абзац — `<p class="mt-6 max-w-3xl text-lg leading-relaxed text-text-muted">`
(на `/uslugi` и `/faq` это `leadParagraph` страницы). Он крупнее по площади,
чем короткий жирный `h1` над ним, поэтому именно его Lighthouse засчитывает
как «largest contentful paint».

**Диагностика шрифтов** — все три пункта из брифа уже выполнены до этой фазы,
менять было нечего:

- У Unbounded два начертания (500 и 700), и оба реально используются: 500 —
  для мелких подписей-капслоков и кнопок (`font-medium`, точное совпадение),
  700 — для заголовков (`font-bold` — точное совпадение; `font-semibold`,
  т.е. 600, у Unbounded не объявлен и по правилам подбора шрифта откатывается
  на ближайший доступный — 700). Третьего начертания в вёрстке нет.
- Preload уже подключается автоматически: `next/font/google` сам добавляет
  `<link rel="preload">` для начертаний, нужных конкретной странице — проверено
  по фактическим сетевым запросам, а не по одному факту наличия тега.
- `subsets: ['latin', 'cyrillic']` уже ограничивает то, что реально
  скачивается. В CSS дополнительно объявлены блоки latin-ext, vietnamese,
  cyrillic-ext и (только у Manrope) greek — но это внутреннее разбиение
  Google Fonts *внутри* запрошенных подмножеств по `unicode-range`, а не
  лишние подмножества: браузер грузит файл только когда на странице
  встречается символ из его диапазона. Прямым замером сетевых запросов
  подтверждено: при заходе на `/uslugi` скачивается ровно 4 файла шрифта
  (Unbounded 500+700 и Manrope 400+600 для символов, реально стоящих на
  странице), vietnamese/greek/latin-ext не запрашиваются ни разу.

Также обнаружено и проверено измерением: у Unbounded оба начертания (500 и
700) физически являются одним и тем же переменным файлом на каждый
unicode-range — хеши файлов совпадают между `font-weight:500` и
`font-weight:700` в сгенерированном CSS. То же самое для Manrope 400/600.
Значит «оставить только одно начертание» не сэкономило бы ни байта: с двумя
начертаниями Google уже отдаёт один файл, урезание списка убрало бы только
объявление в CSS, а не скачивание.

**Экспериментальная мера сверх брифа.** LCP-элемент рендерится шрифтом
Manrope (`swap`), и есть задокументированное поведение Chrome: при
`font-display: swap` итоговый LCP-таймстамп текстового узла фиксируется в
момент подмены на веб-шрифт, а не в момент первой отрисовки фолбэком — то
есть медленная загрузка шрифта может задержать именно LCP, а не FCP.
Проверил это предположение: временно переключил Manrope на
`font-display: optional` (браузер не ждёт и не подменяет шрифт, если он не
готов почти мгновенно), пересобрал и измерил LCP на `/uslugi` и `/faq` по
три прогона на каждой странице:

```
/uslugi:  2524, 2111, 2516 мс
/faq:     2507, 2131, 2579 мс
```

Разброс между прогонами (± 400 мс) больше предполагаемого эффекта меры —
устойчивого выигрыша нет. Изменение отменено, `font-display: swap` вернул
без изменений.

**Фактический источник ~2.5 с.** Прогнал те же страницы с отключённым
троттлингом (`throttlingMethod: 'provided'`, замер в реальном времени вместо
симуляции): LCP на `/uslugi` — 58 мс, на `/faq` — 81 мс. Разбивка LCP из
самого Lighthouse (`lcp-breakdown-insight`) тоже показывает всего
~85–90 мс суммарно (time to first byte + render delay). Разрыв между этой
цифрой и заявленными 2500+ мс целиком на совести симуляции мобильной сети
и CPU у Lighthouse (Lantern, throttling по умолчанию) — она моделирует
загрузку всей цепочки, ведущей к первой отрисовке (в первую очередь JS- и
CSS-бандл), для условного медленного 4G, а не что-то специфичное для
шрифтов или контраста.

**Итог.** Цель «LCP ≤ 1.5 с» под стандартной методикой Lighthouse mobile
(с симулированным троттлингом) **не достигнута** ни до, ни после этой фазы —
см. таблицу ниже, разница в пределах шума прогонов. Все три предписанных
меры по шрифтам уже были на месте, а четвёртая, опробованная по итогам
диагностики, реального эффекта не дала. Оставшееся узкое место — вес и
время разбора JS/CSS-бандла под симулированным троттлингом, а не шрифты;
трогать его в этой фазе не входило в задачу («не оптимизировать
производительность заранее»).

движения ни в плюс, ни в минус нет, что само по себе ожидаемо: страница не
менялась по весу, только цвет текста.
